## Framebuffer failure analysis

- Physical observation: the user reported full-screen violet before the continuous rerun; no synchronized final photo or reconfirmation was collected.
- Application evidence: all six rectangles were submitted and `FB test finished` returned; the OS remained responsive.
- Configuration evidence: `CONFIG_FB_UPDATE=y`, 390×450 RGB565, stride 780.
- Code-path evidence: the first full-screen update uses the driver's tightly packed 24-row chunk path. Each later rectangle has a source stride larger than its row width and therefore uses the one-row-at-a-time partial-update path.
- Current hypothesis only: investigate the CO5300 partial-area transfer path if a controlled visual rerun confirms missing nested rectangles. Current evidence does not establish a refresh defect or its cause.
- Scope boundary: no shared upstream component was modified during this diagnosis.

- One `poll returned: 1` line was observed, but no `PA43_KEY2 was pressed` or `released` line followed, so H3 is not marked passed.
- The example launches a persistent `button_daemon`. Attempts to terminate PID 15 with `kill 15` and `kill -9 15` did not remove it; the board was intentionally not reset merely to clean up this diagnostic task.

- After the user confirmed readiness, a 25-second serial window contained no press/release event. The conversation does not explicitly confirm two physical press/release actions during that window; the earlier description of a controlled two-press retry was overstated. H3 remains unverified, not evidence of a faulty switch.
